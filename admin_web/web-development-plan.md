# خطة تطوير الويب — نظام الأمان الذكي

الهدف تسليم واجهة Flutter Web للمالك ولوحة الأدمن فوق مشروع `admin_web`، بقياس القبول على `SRS_نظام_الأمان_الذكي_v1.0` ومهام `WEB-*` في خطة التطوير v1.0. كل تحكم وتشغيل يمر عبر HTTPS إلى باك إند `security_backEnd`؛ لا اتصال مباشر بالجهاز أو MQTT من المتصفح.

## ما هو موجود ولا يُعاد بناؤه

- عقد السلوك في SRS: أربعة مؤشرات منفصلة، الحالة المؤكدة ≠ نجاح HTTP، PENDING عرض محدود، عزل سجلات المالك عند النقل، الأدمن بلا أوامر تشغيل افتراضية على أجهزة المالك.
- مسار السلامة المحلي على العتاد؛ الويب لا يستبدل الإنذار المحلي.
- إعداد Wi-Fi المحلي (`FR-036`) مسار هاتف/جهاز ميداني — خارج نطاق المتصفح المعتاد.
- دلالات النماذج والحالات يُفضَّل مطابقتها لعميل `security_mobile` دون إعادة تعريف enums الخادم.
- Backend T-02 نفذ وفق تقارير Cursor مسارات `/api/auth/login` و`refresh` و`logout` و`logout-all` و`me` وإدارة حسابات المالك؛ العقود الفعلية تُراجع من OpenAPI قبل الربط، ولا تُعامل واجهات الأجهزة/التنبيهات كمنفذة.
- تصميم المصادقة المعتمد للمتصفح: Access JWT في الذاكرة فقط؛ Refresh في Cookie `HttpOnly; Secure`؛ CSRF موقّع مرتبط بالجلسة مع Origin صحيح؛ `single-flight` لتجديد الرمز؛ لا رمز وصول أو تجديد في Web Storage؛ مسح الحالة عند الإبطال/الخروج. إعدادات `SameSite`/`Path`/`Domain` وCORS وCredentials تعتمد على نطاقات البيئة الفعلية.
- الربط الأولي = `PENDING` محدود، أما نقل الملكية فينشئ `ACTIVE` على الخادم ويُسمح بطلب الأمر عند اتصال الجهاز وفق ضوابط الخادم، مع حجز نشره حتى إقرار `ownershipVersion`؛ يُمنع بقاء بيانات المالك السابق في Cache الواجهة عند فقد التفويض.
- استجابة HTTP لإنشاء الأمر لا تؤكد حالته؛ `COMMAND_ACK` يحمل الحالة الفعلية الكاملة و`resultStateSequence`، مع اعتماد G1 المطلوب قبل إغلاق المسارات الإنتاجية.

## ما يُبنى

- **مسار المالك:** دخول، قائمة أجهزة، تفاصيل وأوامر ARM/DISARM/MUTE/TEST، سجل حوادث/أوامر، وضوح PENDING/REJECTED/TIMED_OUT والحالة القديمة.
- **لوحة الأدمن:** حسابات، تسجيل أجهزة، ربط/نقل/إلغاء، عرض حالات وتشخيص إداري، سجلات إدارة، تنبيه إداري وتتبع محاولة الإرسال عبر API.
- عميل API واحد ونماذج مشتركة المعنى مع الموبايل؛ فصل الشاشات والصلاحيات بين المالك والأدمن، مع فرض التفويض على الخادم وعدم اعتبار إخفاء الأزرار حماية.
- **FCM:** لا يُنفَّذ في الويب. العميل على `security_mobile`؛ الإرسال والأسرار على `security_backEnd`. الويب يعرض فقط نتيجة التسليم التي يعيدها الخادم للتنبيه الإداري.

## المراحل

1. **تأسيس Flutter Web.** `WEB-01` — RTL، توجيه، بيئات، حماية مسارات الجلسة.
2. **عميل API والنماذج.** `WEB-02` — ربط عقود Auth المنفذة مع Access في الذاكرة وRefresh عبر Cookie/CSRF/Origin و`single-flight`، واستعادة جلسة بعد إعادة التحميل بطريقة آمنة، ثم نماذج أجهزة/حالات/أوامر/أخطاء؛ لا enum مجهول كنجاح.
3. **واجهة المالك — القائمة.** `FR-009` `FR-035` — الربط الأولي PENDING محدود؛ النقل ACTIVE على الخادم مع السماح بطلب أمر عند الاتصال واحتجاز نشره حتى مزامنة الملكية؛ المؤشرات الأربعة للحالة المؤكدة ووقت آخر تحديث.
4. **واجهة المالك — التفاصيل والأوامر.** `FR-010`…`FR-018` — لا قلب مؤكد عند HTTP؛ ACK يحمل الحالة الفعلية لا التسلسل وحده؛ تعطيل المتعارض حتى المصالحة بعد TIMED_OUT؛ MUTE بمعرف الحادثة؛ لا إغلاق قبل G1 واختبار توافق.
5. **سجل المالك.** `FR-023` `FR-032` — إنذار/اختبار/تأخر/wasBuffered؛ منع رابط جهاز أجنبي.
6. **لوحة الأدمن.** `FR-002` `FR-003` `FR-004` `FR-006` `FR-007` `FR-008` `FR-026` `FR-033` — حسابات المالك عبر API T-02 المنفذة، وأجهزة/ربط/نقل وسجلات/تنبيه عند تسليم APIs الخاصة بها؛ بلا أوامر مالك افتراضياً؛ تدقيق الإدارة على الخادم غير مرادف لتوفر API استعراض السجلات.
7. **اختبارات القبول.** `WEB-07` — جلسة وتجديد متزامن وCSRF/Origin واستعادة بعد reload وإبطال الحساب؛ أمر ناجح/مرفوض/مهلة، نقل ملكية، تفويض فعلي للخادم، وإزالة Cache عند فقد الملكية.

## ترتيب التنفيذ

المهام في `web-development-tasks.md` تتبع هذا الترتيب. يمكن بدء `T-01` بهيكل مستقل، و`T-02` بعقد المصادقة المنفذ في Backend بعد مطابقته فعلياً؛ يمكن محاكاة APIs غير المنفذة فقط، دون الادعاء بأنها جاهزة. اعتماد عقد HTTP المشترك وG1 من `integration` لا يزال مطلوباً للمسارات التابعة له. لا تُغلق أوامر المالك (`T-04`) إلا بعد ACK/حالة. البيئات في `ops`. قياس القبول عبر `integration/integration-acceptance-matrix.md`.
