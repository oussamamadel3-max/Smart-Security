## قرارات وموانع

- `D-09`: قرار تمثيل `COMMAND_ACK` **موثّق**: يحمل الحالة الفعلية كاملة مع `resultStateSequence`؛ لا يعني ذلك اعتماد عقد الرسائل كاملاً.
- معلّق: استكمال القيم التشغيلية غير المحسومة من `D-03` واعتماد `G1` للمخططات الكاملة واختبارات ترتيب `ACK` و`STATE`.
- بعد T-04: خط أنابيب وارد تطبيقي موجود؛ **استقبال MQTT الحي عبر Mosquitto غير منجز** (`Mqtt:Inbound:Enabled=false` بلا محوّل اشتراك). **اعتماد G1 غير منجز**.
- عامل نشر Outbox / إغلاق صف الأمر من ACK يبقى في **T-05** (بعد G1 للإغلاق الإنتاجي). اختبار MQTT حقيقي شامل في **T-10**.
- `SS-P2-020`/`SS-P2-030`: مسودة `OWNERSHIP_SYNC` وواجهة إبطال Broker موجودتان؛ محوّل Mosquitto الحقيقي/AC-T-19 ما زالا مطلوبين.
- يعتمد لاحقاً على: مسودة/اعتماد عقد MQTT من `integration`، قرارات عتاد من `security_esp`، مكدس محلي من `ops`.

## ما أُنجز فعلياً (حتى الآن)

- هيكل Clean Architecture + Identity بـ Guid + ترحيلات الجداول التشغيلية.
- قيود PostgreSQL واختبارات تكامل لها.
- `GET api/auth/me` محمي؛ عقد أخطاء موحّد.
- بحسب تقرير Cursor المعتمد لـ T-02: JWT/Refresh دوّار/Replay Detection، إدارة جلسات وإبطال فوري، CSRF موقّع للويب، صلاحيات ADMIN/OWNER، إنشاء/تعديل/تعطيل/أرشفة مالك وتدقيق `audit_logs`.
- `BE-02/SS-P2-010`…`SS-P2-030` / T-03: تسجيل وربط PENDING وإقرار وأرشفة مع Broker No-Op تطويري.
- `T-04` (2026-11-06): `DeviceInboundTelemetryService` يتحقق ويحدّث `device_states` مع `FOR UPDATE`؛ HEARTBEAT لـ `last_seen_at` فقط؛ COMMAND_ACK يحدّث الحالة الفعلية دون إغلاق الأمر؛ API مالك بأربعة مؤشرات محسوبة بلا `is_online`.
- `T-09` (2026-11-06): API `push_tokens`؛ عامل إرسال خلف `FakeFcmProvider`؛ `notification_deliveries`؛ Guard قبل الإرسال؛ حمولة معرفات؛ Firebase عبر ADC جاهز لكن **غير مفعّل**.
- لا مسارات أوامر إنتاجية / اشتراك Mosquitto حي / FCM إنتاجي مفعّل بعد.
