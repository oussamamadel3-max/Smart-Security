# سياق المشروع — الموبايل (`security_mobile`)

آخر تحديث: 2026-11-17  
السياق العام: [`../system-context.md`](../system-context.md) · التقدّم: [`mobile-progress.md`](./mobile-progress.md)

## الهوية

| الحقل | القيمة |
|--------|--------|
| المسؤولية | تطبيق مالك Flutter (Android/iOS): جلسة، أجهزة، أوامر، سجلات، FCM عميل، Wi-Fi محلي |
| التقنية | Flutter · RTL عربي · flavors dev/staging/prod · يعتمد على `packages/smart_security_app_core` |
| مسار العمل | `security_mobile/` — T-01 مغلقة؛ T-02 التالية بانتظار موافقة التنفيذ |
| لا يملك | لوحة أدمن · MQTT مباشر · إنذار محلي · عامل FCM على الخادم |

## مبادئ ملزمة

- التطبيق لا يتصل بـ MQTT ولا يستبدل الإنذار المحلي.
- نجاح HTTP لا يقلب المؤشرات المؤكدة؛ الحالة من الخادم بعد تأكيد الجهاز.
- لا أسرار خادم أو مفاتيح خاصة أو اعتمادات إنتاج داخل Git. إعدادات عميل Firebase العامة (مثل App ID/API Key) ليست أسرار خادم بذاتها، لكنها تُراجع وتُقيّد بحسب البيئة ولا تُخلط مع مفاتيح FCM Service Account أو APNs الخاصة.
- إعداد/تغيير Wi-Fi محلي بين التطبيق والجهاز فقط — لا تخزين كلمة المرور في الخادم.
- عقد المصادقة المنفّذ في Backend T-02: Access JWT قصير العمر في الذاكرة، وRefresh دوّار في التخزين الآمن للنظام بالموبايل؛ يُرسل في جسم طلب HTTPS. يُمنع تجديدان متزامنان للرمز نفسه عبر single-flight.
- الربط الأولي PENDING يعرض معلومات محدودة؛ نقل الملكية ينشئ ملكية ACTIVE خادمياً، ويجوز للمالك الجديد المتصل جهازه **تقديم طلب أمر** وفق قيود الأوامر؛ يحتجز الخادم **نشر الأمر وتنفيذه** حتى تأكيد مزامنة إصدار الملكية على الجهاز.
- تنفيذ Backend T-02 لا يعني اعتماد كل عقد HTTP المشترك أو اجتياز G1/G2، ولا يعني وجود كود Flutter.

## قرار عقد 2026-11-16 — للواجهة لاحقاً، بلا تنفيذ Flutter الآن

- الحادثة تبقى جارية بعد كتم الصفارة. لا تعرضها منتهية إلا بعد حالة `ENDED` القادمة من الخادم.
- `202` و`PENDING` ليسا تنفيذ أمر. لا MQTT من التطبيق.
- لا شاشة `SETTINGS_SYNC` أو OTA في v1.
- مهلة 60 دقيقة و10 ثوانٍ و30 ثانية أرقام اختبار، لا نصوص إنتاج نهائية في الواجهة.

## قرارات وموانع

- المصادقة والجلسات وإدارة المالك منفّذة في Backend T-02 بحسب تقرير Cursor؛ يجب مطابقة عميل Flutter مع OpenAPI/التنفيذ الفعلي، لا اختراع عقد آخر. بقي توحيد عقد HTTP لجميع مسارات الأجهزة والأوامر والأحداث ضمن `integration` T-03 واعتماد G1 عند الاقتضاء.
- FCM جانب الخادم في `security_backEnd`؛ مسار الهاتف هنا فقط.

## ما أُنجز فعلياً (حتى الآن)

- تأسيس `packages/smart_security_app_core` (ضمن نطاق T-01 الموسَّع).
- Scaffold Flutter Android/iOS في `security_mobile` مع path إلى الحزمة.
- ثيم فاتح من `design/index.html`؛ أخطاء Backend المؤكدة؛ بدون AuthInterceptor في الحزمة.
- حُذفت نسخة `app_core/` القديمة في 2026-11-17 بعد التحقق من عدم استيرادها. المصدر هو `packages/smart_security_app_core`.
- تشغيل Android على جهاز/محاكٍ وبناء iOS مؤجّلان بموافقة المالك (`NOT VERIFIED`) وليسا جزءاً من دليل إغلاق T-01.

## قواعد إضافة كود Flutter

| أضف إلى `packages/smart_security_app_core` | أبقِ في `security_mobile` |
|--------------------------------------------|---------------------------|
| توكنات ثيم، أخطاء عامة، Dio أساسي، ترجمة عامة، ويدجتات عامة | Auth body refresh، Secure Storage، FCM، Wi-Fi، Router، الشاشات |
| مسارات Auth الافتراضية المؤكدة فقط | أي Endpoint/DTO أعمال بعد اعتماد العقد |

## قواعد تحديث هذا الملف

1. عند بدء/إنهاء مهمة: حدّث الجدول والملخص، وزامن `mobile-current.md`.
2. عند ربط عقد API أو Firebase: سجّل الحالة دون وضع أسرار.
3. لا تكرر تفاصيل القبول هنا.
4. بعد تحديث جوهري: انسخ الملخص إلى [`../system-context.md`](../system-context.md).
