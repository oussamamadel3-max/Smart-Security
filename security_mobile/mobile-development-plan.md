# خطة تطوير الموبايل — نظام الأمان الذكي

الهدف تسليم تطبيق Flutter للمالك على Android وiOS فوق مشروع `security_mobile`، بقياس القبول على `SRS_نظام_الأمان_الذكي_v1.0` ومهام `MOB-*` / `FCM-*` في خطة التطوير v1.0. التحكم المعتاد يمر عبر HTTPS إلى باك إند `security_backEnd` فقط.

## ما هو موجود ولا يُعاد بناؤه

- عقد السلوك في SRS: أربعة مؤشرات منفصلة (اتصال، حماية، صفارة، عتاد)، الحالة المؤكدة ≠ نجاح HTTP؛ الربط الأولي PENDING عرض محدود، أما نقل الملكية فيُنشئ ACTIVE على الخادم مع جواز تقديم طلب أمر حين يكون الجهاز متصلاً واحتجاز نشره حتى تأكيد OWNERSHIP_SYNC؛ النقل يعزل سجلات المالك السابق.
- مسار السلامة المحلي على العتاد؛ التطبيق لا يستبدل الإنذار المحلي ولا يتصل بـ MQTT لأوامر التشغيل.
- استثناء وحيد للاتصال المحلي بالجهاز: إعداد/تغيير Wi-Fi وفق `FR-036` بعد تحقق الصلاحية والحيازة.
- نماذج الحالة والأوامر والأخطاء يُفضَّل مشاركتها منطقياً مع عميل الويب عند توفّره؛ الموبايل لا يعيد تعريف دلالات الـ enum في الخادم.
- Backend T-02 نفّذ Login/Refresh/Logout/Logout-all/Me وإدارة المالك: Access JWT في الذاكرة بالموبايل وRefresh عشوائي دوّار في التخزين الآمن للنظام، يُرسل في جسم HTTPS، ويُستبدل بأمان بعد التجديد؛ لا يُستخدم Cookie الويب في العميل الأصلي.
- لا يصدر التطبيق أو يثق بحالة COMMAND_ACK من تلقاء نفسه: ACK يتضمن الحالة الفعلية الكاملة مع resultStateSequence وفق القرار المحدد، مع بقاء تجميد العقد النهائي رهناً بـG1.

## ما يُبنى

تطبيق مالك: جلسة وRTL وتوجيه، قائمة الأجهزة والتفاصيل، أوامر ARM/DISARM/MUTE/TEST مع PENDING والتأكيد والمهلة، سجل الحوادث/الأوامر، إشعارات FCM وربطها بـ eventId من الخادم، وإعداد Wi-Fi المحلي. لا لوحة أدمن على الهاتف في نطاق المالك. لا أسرار خادم FCM داخل التطبيق.

## المراحل

1. **تأسيس المشروع والبيئات.** `MOB-01` — Android/iOS، flavors للتطوير/الاختبار/الإنتاج، توقيع داخلي، RTL وتوجيه وحماية المسارات.
2. **عميل API والجلسة.** `FR-001` — مطابقة API المصادقة المنفّذ في Backend T-02؛ دخول/خروج/تجديد واستعادة الجلسة؛ Access في الذاكرة وRefresh في التخزين الآمن؛ single-flight لمنع تدوير متزامن، مع حفظ الرمز الجديد قبل إطلاق الطلبات المنتظرة؛ إبطال محلي آمن عند رفض التجديد نهائياً أو تعطيل الحساب؛ 401 يختلف عن 403 ولا تُسجّل الرموز في السجلات.
3. **قائمة الأجهزة والمؤشرات.** `FR-009` `FR-027` `FR-028` `FR-035` — ربط أولي PENDING محدود؛ نقل ملكية ACTIVE خادمياً مع السماح بتقديم طلب عند الاتصال واحتجاز نشره حتى تأكيد إصدار الملكية؛ عرض المؤشرات الأربعة ووقت آخر تحديث؛ إخلاء البيانات المحلية عند زوال التفويض؛ لا خلط بين الانقطاع وتعطيل الحماية.
4. **التفاصيل والأوامر.** `FR-010`…`FR-018` — استجابة إنشاء الأمر PENDING لا تغيّر الحالة المؤكدة؛ EXECUTED لا تُعرض إلا مع الحالة الفعلية المؤكدة من الجهاز وresultStateSequence؛ TIMED_OUT نتيجة مجهولة لا تُفسّر كفشل تنفيذ؛ تعطيل المتعارض حتى المصالحة؛ MUTE يرسل معرف الحادثة الجارية.
5. **السجلات والحوادث.** `FR-023` `FR-032` — تمييز إنذار/اختبار/تأخر/wasBuffered؛ منع فتح جهاز أجنبي عبر الرابط؛ تفاصيل الحادثة من API بعد الإشعار.
6. **FCM على الجهاز.** `FCM-01` و`FCM-03`/`FCM-05`/`FCM-06` (عميل) + `MOB-04`…`MOB-06`: إعداد Firebase وAPNs لكل بيئة، تحديث/إلغاء رمز الجهاز عند التغيير أو تبديل الحساب والخروج، حالات foreground/background/terminated؛ فتح الحادثة يستلزم إعادة جلبها وفحص الملكية الخادمي، ولا بيانات حساسة على شاشة القفل. إعدادات Firebase العامة للعميل ليست أسرار خدمة FCM؛ أسرار إرسال الخادم (`FCM-02`/`FCM-04`) في `security_backEnd` فقط.
7. **Wi-Fi المحلي.** `FR-036` — مسار الفني/المالك عبر شبكة مؤقتة محمية وحيازة فعلية؛ لا تخزين كلمة مرور الشبكة في الخادم؛ لا أوامر حماية عبر هذا المسار؛ لا تُعرض نتيجة نجاح حتى يثبت اتصال الجهاز بالشبكة الجديدة، ويبقى مسار الإنذار المحلي مستقلاً.
8. **اختبارات القبول للواجهة.** شبكة ضعيفة، إذن مرفوض، هاتفان لنفس الحساب، إشعار بعد النقل، أوامر معلّقة/مرفوضة/منتهية — بما يغطيه الموبايل من سيناريوهات الخطة.

## ترتيب التنفيذ

المهام في `mobile-development-tasks.md` تتبع هذا الترتيب. يمكن البدء بـ`T-01` دون انتظار Backend؛ وفي `T-02` يُستخدم عقد المصادقة المنفّذ فعلياً في Backend مع تحقق HTTP، لا عقد مُختلَق. بقية المسارات تحتاج توحيد OpenAPI في `integration`، ولا تُغلق تدفقات الأوامر (`T-04`) إنتاجياً قبل اعتماد G1 واختبار ACK والحالة. اختبارات الموبايل النهائية (`T-08`) تشمل Wi-Fi المحلي (`T-07`) على جهاز حقيقي حين يجهز العتاد. البيئات التشغيلية في `ops`، والقبول عبر `integration/integration-acceptance-matrix.md`.
