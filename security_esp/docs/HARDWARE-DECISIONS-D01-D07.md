| ما يحتاج قياساً/اعتماداً | حجم نطاق الحجز الأمثل (موازنة بين تآكل الفلاش وفقدان تسلسل محتمل عند انقطاع مفاجئ) — لا يُعتمد تصميم نهائي قبل اختبار انقطاع الطاقة الفعلي (`T-05`/`T-09`). |

## D-06 — سياسة الاحتفاظ بالأحداث المحلية وحذفها (نطاق الجهاز فقط)

| الحقل | القيمة |
|---|---|
| توضيح نطاق | `D-06` في خطة التطوير العامة يغطي حذف/أرشفة/احتفاظ على مستوى النظام (ملك الباك إند/قاعدة البيانات). ما يخص `T-01`/ESP هنا هو **الاحتفاظ المحلي داخل طابور أحداث الجهاز فقط**، لا سياسة الأرشفة العامة. |
| المبدأ المقترح | لا يُحذف أي حدث محلي قبل استلام `EVENT_PERSISTED` من الخادم يحمل نفس `alarmPhase`/`eventUid` (مبدأ ثابت في خطة ESP). **تصحيح (2026-11-18، ESP-C-05):** هذا الصف كان يذكر سابقاً "استبدال الأقدم" عند امتلاء الطابور، وهو يتعارض مباشرة مع "لا حذف قبل EVENT_PERSISTED" في الجملة نفسها. السلوك الصحيح المطابق للمنفَّذ والمختبَر فعلياً في `event_queue.c`: عند الامتلاء، **الحدث الجديد** هو ما يُرفض/يُفقَد (لا يُخزَّن)، وتُرفع علامة فقد مستقلة (`wasBuffered`/علامة فقد)؛ أي حدث موجود مسبقاً وغير مؤكَّد **لا يُخلى أبداً** لإفساح المجال لحدث جديد. |
| ما يحتاج قياساً/اعتماداً | السعة العددية للطابور (مرتبطة بـ `D-03`)؛ مكان/شكل علامة الفقد (حيز مستقل أو محجوز) يُحسم في `T-05`. |
| الدليل المطلوب | اختبار امتلاء الطابور لا يوقف الإنذار المحلي ويُظهر علامة الفقد عند الاتصال (`T-05` قبول، معادل لـ `AC-T-09`). |
| المالك | فريق العتاد/ESP (نطاق الجهاز) — سياسة الاحتفاظ العامة على مستوى النظام تبقى مع `security_backEnd`/`DB`، خارج هذا البند. |
| الحالة الرسمية | **مبدأ "لا حذف قبل EVENT_PERSISTED" معتمد؛ السعة والتنفيذ التفصيلي مفتوحان حتى `T-05`.** |

## D-07 — ربط هوية الجهاز بقرار الباك إند (مرجعي، ليس قراراً مستقلاً لـESP)

| الحقل | القيمة |
|---|---|

| ما يحتاج قياساً/اعتماداً | لا شيء إضافي من جهة ESP؛ أي تغيير في شكل المفتاح من جهة الباك إند يتطلب مراجعة `integration` قبل الاعتماد في firmware. |

## سياسة السلامة S1 — تلف إعداد الحماية / فقد كل مصادر الطاقة ثم العودة

| الحقل | القيمة |
|---|---|
| القرار المعتمد (مالك 2026-11-21) | **S1** — تفصيل ملزم أدناه. |
| 1) إعادة تشغيل طبيعية مع تخزين سليم | استعادة **آخر إعداد حماية موثوق وصحيح** من التخزين غير المتطاير. إعادة التشغيل الطبيعية **ليست** سبباً لإلغاء إعداد حماية سليم. |
| 2) تلف الإعداد أو تعذر استعادة موثوقة | الجهاز يبقى **غير مسلّح محلياً** (`DISARMED` تشغيلياً) و**لا يتسلّح تلقائياً**. لا مسار fail-secure صامت إلى `ARMED`. |
| 3) الإعلان للمستخدم/الخادم | إعلان صريح عن العطل وعدم اليقين؛ **عدم** عرض الجهاز باعتباره محمياً بصورة مؤكدة. |
| 4) العودة للتشغيل الطبيعي | فقط بعد استعادة إعداد حماية موثوق **بتدخل المالك** (أمر/إجراء صريح)، لا بمجرد عودة الطاقة أو إعادة الإقلاع. |
| 5) فصل الحالات | فصل **الحالة التشغيلية الفعلية** (ماذا يفعل الجهاز محلياً) عن **حالة المعرفة المعروضة** للمستخدم/الواجهة. |
| تمثيل عقدي مسموح دون حقول جديدة (مسودة v1) | استخدام القيم الموجودة: `armState=DISARMED` أو `UNKNOWN` للمعرفة غير المؤكدة؛ `healthState=FAULT` أو `UNKNOWN`؛ و/أو `DEVICE_FAULT` بـ `faultCode` مفتوح النص (مثلاً توصية توثيقية غير مجمّدة: `CONFIG_CORRUPT` / `CONFIG_RESTORE_FAILED`) ضمن المخطط الحالي. **لا** يُضاف `messageType` أو enum جديد دون موافقة مستقلة. |
| فجوة تمثيل مسجّلة (INT-T-01) | العقد الحالي **لا يميّز دلالياً** بين `DISARMED` باختيار المالك و`DISARMED` بسبب استرداد S1، ولا بين `UNKNOWN` المؤقت و«استرداد آمن معلن». المقترح للمعالجة اللاحقة (خارج نطاق تثبيت حقل الآن): (أ) اصطلاح `faultCode` موثّق في G1، أو (ب) حقل اختياري جديد بعد موافقة مالك/Integration — يُحال إلى مراجعة G1/`INT-T-04` دون تنفيذ هنا. |
| أثر متوقع | Firmware: استعادة NVS + مسار استرداد. Backend/Flutter: لا تعرض «محمي مؤكد» عند `UNKNOWN`/`FAULT` أو عطل استرداد. Integration: لا حقول جديدة في هذه المهمة. |
| الدليل المطلوب | تحقق عتادي + اختبارات (`DEP-SAFE-01`). |
| المالك | منتج + ESP (+ Backend/Flutter/Integration للأثر العرضي) |
| الحالة الرسمية | **`OWNER APPROVED — S1 — VALIDATION PENDING`.** |

## قائمة القطع الأولية (BOM) — مرجع أولي غير معتمد للشراء أو الإنتاج

| # | القطعة | الدور | ملاحظة |
|---|---|---|---|
| 1 | ESP32-WROOM-32 (DevKitC أو معادل) | متحكم رئيسي | راجع D-01؛ لا اعتماد نهائي قبل T-02 |
| 2 | وحدة SW-420 | استشعار اهتزاز | خرج رقمي + حساسية قابلة للتعديل عبر مقاومة متغيرة |
| 3 | صفارة/جرس 12V | إنذار صوتي | استهلاك التيار الفعلي يُقاس في T-02 |
| 4 | مرحل أو MOSFET قناة-N + دائرة قيادة | قيادة الصفارة من منطق 3.3V | يتضمن diode حماية إن كانت الصفارة كهرومغناطيسية |
| 5 | بطارية 12V مستقلة (مفترضة الشحن) | تغذية احتياطية/أساسية محلية | ليست اختيارية؛ سعتها الفعلية تُقاس في T-02 |
| 6 | منظم خفض (buck) 12V→5V/3.3V | تغذية منطق ESP32 | رقم القطعة النهائي مفتوح |
| 7 | مصهر/PTC + صمام حماية عكس القطبية + TVS | حماية كهربائية | إلزامي قبل أي تشغيل فعلي بالـ12V (راجع T-02 "سجل سلامة كهربائية") |
| 8 | LED حالة + زر تهيئة محلي (اختياري v1) | تشخيص/دخول وضع التهيئة (`FR-036`) | يُفصَّل في T-08 |

**قرار مالك 2026-11-21:** هذا الجدول **مرجع أولي غير معتمد** للشراء أو الإنتاج. تأجيل اعتماد القطع (D-01) يمنع اعتبار أي صف هنا قطعة نهائية. لا تثبيت ميداني قبل قرار مالك لاحق + مراجعة `T-02` الكهربائية.

## مخطط التوصيل الأولي (نصي، للمراجعة قبل رسم مخطط EDA رسمي)

```
[بطارية 12V مستقلة] --+-- [مصهر/PTC] --+-- [منظم خفض 12V→5V/3.3V] --> ESP32 (3V3/GND)
                       |                |
                       |                +-- (12V مباشر، عبر حماية عكس القطبية) --> خط الصفارة
                       |
                       +-- [صمام عكس القطبية] (حماية خط التغذية الرئيسي)

ESP32 GPIO_x  --> [مدخل تحكم المرحل/MOSFET] --> [صفارة 12V] <-- [12V من البطارية عبر الحماية]
                                                     |
                                              [diode حماية] (إن كانت الصفارة كهرومغناطيسية)

SW-420 VCC  <-- 3.3V (من ESP32 أو المنظم)
SW-420 GND  <-- GND مشترك
SW-420 DOUT --> ESP32 GPIO_y (مدخل رقمي، مقاطعة/استقصاء)

ESP32 GPIO_z --> LED حالة (عبر مقاومة تحديد تيار)
ESP32 GPIO_w <-- زر/مفتاح دخول وضع التهيئة المحلي (FR-036، يُفصَّل في T-08)
```

هذا مخطط مبدئي لمراجعة التوصيل المنطقي فقط (أي خط يتصل بأي خط)؛ لا يُعتمد كمخطط EDA نهائي ولا يُستخدم للتصنيع قبل مراجعة `T-02` وقياس الأحمال الفعلية.

## خطة معايرة الحساس (SW-420) — مسودة لـ T-01، تُنفَّذ فعلياً في T-02/T-03

1. تثبيت SW-420 على سطح الاختبار بنفس طريقة التركيب الميدانية المتوقعة (تقليل الاهتزاز الطفيلي من التثبيت نفسه).
2. تسجيل عدد النبضات الناتجة عن: (أ) اهتزاز بيئي عادي (خلفية)، (ب) محاولة تخريب محاكاة (طرق/هز متكرر)، لمدة اختبار ثابتة لكل حالة.
3. اختيار N (عدد النبضات المؤهِّلة) ونافذة T بحيث: الخلفية لا تُحقِّق الحادثة، والتخريب المحاكى يُحقِّقها خلال زمن معقول (قيمة الهدف تُحسم بعد القياس، لا تُخمَّن هنا — D-03).
4. تحديد مدة "التبريد" (غياب النبضات) اللازمة قبل اعتبار الحساس "عاد للوضع الطبيعي" وفتح إمكانية حادثة جديدة.
5. توثيق النتائج العددية هنا وفي `esp-progress.md` بعد التنفيذ الفعلي على عتاد حقيقي؛ وضع علامة "غير منفَّذ — يتطلب عتاداً" إلى حين ذلك.

**حالة التنفيذ الفعلي لهذه الخطة: لم تُنفَّذ — لا عتاد متاح في هذه الجلسة.** هذا قسم تخطيطي (D-02) لا نتيجة قياس.

## إعلان بوابة G0

**مسموح الآن (تجارب طاولة محدودة فقط):**
- بناء مشروع ESP-IDF أولي واختبار قراءة SW-420 منطقياً (مع Fake/محفز مُصطنع عند غياب العتاد الفعلي).
- تجربة منطق آلة حالة الحماية والعتبة (`D-02`) على محاكاة/عتاد تجريبي منخفض الجهد، دون الدائرة الكاملة 12V.

**محظور حتى إغلاق G0 على D-01…D-07:**
- تثبيت firmware إنتاج أو جداول تهيئة نهائية.
- تشغيل دائرة الصفارة الكاملة 12V دون سجل سلامة كهربائية من `T-02`.
- اعتماد أي قيمة TTL/سعة/معايرة كقيمة إنتاجية نهائية (تبقى `D-03` مفتوحة).
- تفعيل Secure Boot/Flash Encryption أو أي إعداد أمني غير قابل للعكس.

**العلاقة مع G1:** `G0` لا تنتظر اعتماد `G1` النهائي (مطابق لـ`esp-development-plan.md`)، لكن مسودتي `D-04`/`D-05` تدخلان صياغة عقد `integration` دون اعتماد إنتاجي قبل `G1`.

**حالة البوابة: `G0 NOT CLOSED`.** موافقة المالك 2026-11-21 ثبّتت حالات القرارات أعلاه **دون** إغلاق G0 ودون `APPROVE TASK CLOSURE: ESP-T-01` / `G0`. الإغلاق ما زال يتطلب تلك الصيغة الصريحة بعد سد الاعتماديات العتادية (`docs/gates/G0-G1-remaining-dependencies.md`).
