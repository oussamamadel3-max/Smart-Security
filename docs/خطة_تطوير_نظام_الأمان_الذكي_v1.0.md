__المرجع:__ وثيقة SRS نظام الأمان الذكي v1.0، وتصميم قاعدة البيانات DB v1.0  
__الهدف:__ تنفيذ نظام لموقع واحد يضم جهاز ESP32 واحداً أو أكثر، مع إنذار محلي مستقل عن الإنترنت، وإدارة وتحكم عبر الخادم، وواجهات Flutter Web والهاتف، وإشعارات FCM.

تنقيح تكامل بتاريخ 24 تشرين الأول 2026: حُدّث عقد الرسائل ونقل الملكية وحفظ الحوادث وضوابط الأوامر واختبارات القبول. تبقى القرارات التشغيلية المؤجلة رهن اعتمادها.

تحديث نقاط الحسم بتاريخ 26 تشرين الأول 2026: وُضّحت مسؤولية حفظ طلب الإشعار، وحدود عرض الملكية المعلقة، ونقطة حسم تمثيل الحالة الفعلية في تأكيد الأمر. تبقى قرارات العتاد والقيم التشغيلية وعقد G1 بانتظار اعتماد الفريق.

هذه خطة عمل وترتيب اعتماديات. لا تعني أن النظام منفذ حالياً. القيم الزمنية وطرازات العتاد وسياسات الاحتفاظ التي لم تحددها الوثائق يجب اعتمادها في المرحلة الأولى، ثم تثبيتها في SRS وتصميم قاعدة البيانات وعقود الرسائل.

## <a id="الصورة-النهائية-للنظام"></a>1. الصورة النهائية للنظام

__مسار السلامة المحلي:__ الحساس ← ESP32 ← الصفارة. يعمل دون الخادم والإنترنت ما دامت الطاقة والقطع اللازمة تعمل.  
__مسار التحكم:__ الواجهة ← HTTPS ← الخادم ← MQTT ← الجهاز ← تأكيد الجهاز ← قاعدة البيانات والواجهة.  
__مسار الإنذار البعيد:__ الجهاز ← MQTT ← حفظ الحادثة في PostgreSQL ← طلب إشعار ← FCM ← الهاتف.  
__مصدر الحقيقة:__ آخر حالة أكدها الجهاز، وليست نتيجة طلب HTTP أو وصول رسالة إلى الوسيط. واجهات Flutter لا تتصل مباشرة بالجهاز أو MQTT.

قناة واردة وحيدة للجهاز: EXECUTE_COMMAND وOWNERSHIP_SYNC وEVENT_PERSISTED وSETTINGS_SYNC عند اعتماد التهيئة عن بعد. يحدد messageType مخطط كل نوع؛ لا retained للأوامر اللحظية.

لكل رسالة: schemaVersion, deviceId, messageId, bootId أو آلية تسلسل مكافئة، ووقت الجهاز مع علامة الثقة به. للأمر أيضاً commandId, commandSequence, ownershipVersion, expiresAt, type. للحدث eventUid ثابت عند إعادة الإرسال. يرسل EVENT_PERSISTED بعد نجاح التزام الحفظ في PostgreSQL حتى لو كانت الحادثة موجودة مسبقاً، ولا يعد MQTT PUBACK دليلاً على الحفظ. تحمل OWNERSHIP_SYNC إصدار الملكية وحالة الربط من دون هوية المالك، ويعيدها الخادم عند الاتصال حتى يؤكدها الجهاز؛ يشمل ذلك إلغاء الربط من دون مالك جديد. لا تحفظ أوامر التحكم اللحظية كرسائل retained؛ ويجب ألا ينفذ الجهاز أمراً لا يستطيع التحقق من صلاحيته الزمنية. تضبط ACL بحيث يكتب الجهاز حالته وأحداثه وتأكيداته ويقرأ قناة أوامره فقط، فيما يكتب الخادم الأوامر. يثبت قرار QoS لكل قناة باختبار إعادة التسليم؛ التكرار يعالج بمعرفات الرسائل، وليس بافتراض وصول وحيد. يرسل الحدث wasBuffered عند استعادته من المخزن، ويعرض وقت الاستلام مع وقت وقوع غير مؤكد إذا لم تثبت ساعة الجهاز. يستخدم QoS 1 للأوامر والأحداث وACK وOWNERSHIP_SYNC وEVENT_PERSISTED، وQoS 0 للنبضات الدورية؛ لا retained لأي أمر لحظي. يعاد إرسال OWNERSHIP_SYNC دورياً وعند إعادة الاتصال حتى يقر الجهاز الإصدار.

### <a id="عقد-http"></a>4.2 عقد HTTP

ينشر OpenAPI قبل بناء الواجهات، ويشمل على الأقل: الدخول والجلسة؛ إدارة الحسابات؛ تسجيل الجهاز والربط والنقل وإلغاء الربط؛ قائمة أجهزة المالك وحالة الجهاز؛ إنشاء الأوامر وجلب حالتها؛ الأحداث والأعطال وسجلات الإدارة؛ تسجيل/إبطال مستقبلات الإشعار؛ التنبيه الإداري. تحدد لكل عملية هوية طالبها وصلاحيته ونطاق الملكية، ونموذج الطلب والرد، والأخطاء المتوقعة، والترقيم والفرز. POST الأمر يعيد معرف الأمر وحالته PENDING؛ لا يرد بأن الحماية تغيرت حتى يصل تأكيد الجهاز. POST الأمر يحتاج مفتاح idempotency ويعيد 202 ومعرف الأمر وحالة PENDING؛ يميز العقد 401 للمصادقة و403 لفقد الصلاحية أو الملكية و409 للتعارض أو انتظار المصالحة و503 لتعذر الحفظ أو الخدمة، مع رمز خطأ ثابت. يرفض الخادم رمز حساب معطل في كل عملية محمية.

الملكية

PENDING, ACTIVE, ENDED, CANCELLED

الربط الأولي PENDING بلا تحكم حتى الإقرار؛ النقل يفتح ملكية الجديد ACTIVE فوراً ويسمح بطلب أمر إذا كان الجهاز متصلاً، لكن لا يُنشر ولا ينفذ قبل إقرار الجهاز لإصدار الملكية؛ القديم يفقد وصول API فور النقل.

بوابة العقد G1: أمثلة JSON لأمر وتأكيد وحالة وحادثة وتأكيد حفظها وعطل وربط ونقل وإلغاء ملكية؛ مراجعة مشتركة من مطور ESP32 والباكند وFlutter، ثم اختبار توافق آلي لكل طرف. تبقى الحادثة الجارية مرتبطة بمعرفها بعد كتم صوت الصفارة حتى عودة الحساس للوضع الطبيعي؛ siren_state=OFF لا تعني انتهاء الحادثة. يعتمد تمثيل UTC بصيغة RFC 3339 مع Z؛ يكون expiresAt جزءاً من EXECUTE_COMMAND، ويجب على الجهاز رفضه إذا لم يستطع إثبات الوقت. stateSequence متزايد على مستوى الجهاز عبر إعادة التشغيل، ولا تحرك النبضة وحدها الحالة المؤكدة. تُختبر إعادة التشغيل قبل اعتماد طريقة تخزين التسلسل على العتاد.

قرار D-09 الوظيفي المعتمد: يحمل COMMAND_ACK النتيجة والحالة الفعلية كاملة مع resultStateSequence، إلى جانب تقرير STATE الدوري المستقل. يبقى اعتماد البنية النهائية للحمولة، والتحقق من التسلسل وإعادة التسليم ووصول STATE قبل ACK وبعده، ضمن G1. لا تُحدَّث device_states من رقم التسلسل وحده، ولا يسمح ACK متأخر بإرجاع الحالة إلى تسلسل أقدم.

### 4.4 أمثلة الحد الأدنى لرسائل التكامل

تفرد معرف الجهاز وملكية مفتوحة واحدة؛ إعدادات معتمدة وحالة UNKNOWN وتدقيق في معاملة التسجيل.

DB-03

ترحيل alarm_events أولاً، ثم device_commands وcommand_status_history وoutbox_messages مع FK مركب للحادثة.

لا يشير أمر كتم إلى جدول لم يُنشأ؛ أمر PENDING واحد وتسلسل فريد، وإدراج الأمر وOutbox معاً.

DB-04

ترحيلات device_faults, event_loss_reports, admin_alerts, notifications؛ alarm_events موجودة من DB-03.

إعادة الحدث لا تنشئ صفاً أو إشعاراً ثانياً؛ ينشأ طلب الإشعار في معاملة الحادثة أثناء P3.

DB-05

ترحيلات push_tokens وnotification_deliveries لاستكمال إرسال FCM؛ notifications موجودة من DB-04.

تسجل محاولة لكل هاتف، وتبطل الرموز السابقة عند تبديل الحساب؛ لا يرسل لحساب مالك سابق.

DB-06

استكمال الفهارس المركبة والجزئية وسياسة RESTRICT مع اختبار التنافس على PostgreSQL فعلي.

قيود (device_id,sensor_id) و(device_id,alarm_event_id) تُضاف في ترحيل مصدرها المبكر؛ تختبر هنا أيضاً.

DB-07

اختبار جميع الترحيلات والبذور على قاعدة فارغة، ومراجعة أثرها وطريقة التراجع قبل الإنتاج.

تنشأ بيئة جديدة آلياً مع أدمن DB-01؛ لا يكشف البناء أو الاختبار عن سر البذر في المستودع.

DB-08

استراتيجية النسخ الاحتياطي، الاحتفاظ، استعادة نسخة في بيئة منفصلة

نجاح استعادة كاملة موثقة، لا الاكتفاء بوجود ملف النسخة.

لا تخزن is_online كحقيقة دائمة؛ يحسب من last_seen_at والمهلة. ولا تمحو سجلات ملكية أو أمر أو حادثة بسبب حذف جهاز أو حساب إدارياً. تفاصيل الحقول والقيود في ملف DB المرجعي.

## <a id="مهام-esp32-والعتاد"></a>6. مهام ESP32 والعتاد

__الترتيب__

__المهمة__

__نتيجة الاختبار__

HW-01

بناء دائرة على الطاولة بالحساس والصفارة ودارة القيادة والتغذية؛ اختبار الجهد والتيار والبطارية

صفارة تعمل بأمان، واستمرار الجهاز فترة قياس معلومة عند فقد التغذية الأساسية.

ESP-01

تقسيم firmware إلى إدخال الحساس، آلة الحماية، تحكم الصفارة، التخزين، الشبكة، MQTT، التشخيص

يمكن اختبار القرار المحلي من دون شبكة.

ESP-02

قراءة الحساس ومعايرة شرط الإنذار ومنع حادثة لكل نبضة؛ إبقاء معرف الحادثة الجارية بعد كتم الصوت حتى عودة الحساس إلى الوضع الطبيعي.

حادثة واحدة حتى عودة الحساس للوضع الطبيعي؛ حادثة جديدة بعد ذلك.

ESP-03

تنفيذ ARM, DISARM, MUTE_ALARM, TEST_SIREN, STOP_TEST

الكتم يبقي الحماية؛ اختبار الصفارة يتوقف محلياً؛ الإنذار الحقيقي له الأولوية.

ESP-04

حفظ آخر إعداد حماية مؤكد، ومعرفات الحوادث غير المؤكدة وبيانات الإصدار بذاكرة غير متطايرة

بعد إعادة التشغيل لا يعود الجهاز لحالة مفترضة ولا يفقد حدثاً لم يؤكد الخادم حفظه.

ESP-05

طابور محدود مع مساحة مستقلة أو محجوزة لعلامة الفقد؛ وسم الحدث wasBuffered عند إعادته؛ لا حذف حتى EVENT_PERSISTED.

عند امتلاء السعة يستمر الإنذار المحلي، وتصل علامة فقد عند عودة الاتصال.

ESP-06

تجهيز Wi-Fi أثناء التركيب وMQTT عبر TLS وهوية مستقلة لكل جهاز؛ إعادة الاتصال والنبضات

لا يمكن لجهاز قراءة/نشر قناة جهاز آخر؛ يعيد الحالة والأحداث بعد العودة.

ESP-07

التحقق من معرف الأمر وتسلسله ونسخة الملكية وانتهاء صلاحيته وتنفيذه مرة واحدة؛ استقبال OWNERSHIP_SYNC وإقرار الإصدار حتى عند عدم وجود مالك، ورفض كتم حادثة تغير معرفها

يرفض التكرار والقديم؛ لا ينفذ أمر مؤجلاً مجهول الصلاحية إذا لم يثبت الوقت.

ESP-08

إرسال تأكيد بنتيجة الأمر والحالة الفعلية، مع أوقات الجهاز وعلامة الثقة

تظهر الواجهة النتيجة المؤكدة؛ لا تعتمد على وصول MQTT وحده.

ESP-09

إظهار تشخيص العتاد والطاقة فقط عندما تتوافر دارة قياس مناسبة

UNKNOWN عند غياب التشخيص؛ لا يفترض صدور الصوت من نجاح خرج GPIO.

ESP-10

اختبار الاسترداد من انقطاع كهرباء وشبكة ووسيط وخادم، ثم مسار تحديث firmware المعتمد

لا تنفذ أوامر قديمة بعد العودة؛ توثق كيفية إصلاح جهاز فشل تحديثه.

يبدأ HW-01 وESP-01 مباشرة بعد D-01 وD-02، قبل انتظار اكتمال تطبيقات الويب والهاتف. ينفذ فريق ESP32 اختبارات جهاز فعلي وجهاز ثانٍ للتحقق من عزل القنوات. إذا اعتمد ESP-IDF، تثبت نسخة SDK والمكوّنات في المشروع، وتراجع خيارات Secure Boot وFlash/NVS Encryption مع خطة الإصلاح والتحديث قبل تمكينها على أجهزة الإنتاج.

## <a id="مهام-الباكند-asp.net-core"></a>7. مهام الباكند ASP.NET Core

__تنظيم مقترح:__ API للطلبات؛ خدمات تطبيق لقواعد الملكية والأوامر والحوادث؛ طبقة تخزين EF Core؛ عامل خلفي لـMQTT/Outbox والإشعارات. يمكن تشغيل العامل في عملية مستقلة عند الحاجة، مع بقاء العقود وقاعدة البيانات مشتركة. لا يتخذ Controller قرار تنفيذ جهاز من مجرد استجابة الوسيط.

__الترتيب__

__المهمة__

__معيار الإنجاز__

BE-01

تأسيس المشروع والتهيئة والهوية والصلاحيات ونموذج الأخطاء وOpenAPI

كل endpoint محمي على الخادم؛ طلبات الأجهزة الأجنبية ورموز الحسابات المعطلة مرفوضة فوراً.

BE-02

إدارة الحسابات وتسجيل الأجهزة والاعتماد المنفصل والربط الأولي PENDING ومزامنة إصداره وإقراره

لا معرف مكرر ولا ربط لمالك ثانٍ.

BE-03

نقل/إلغاء الربط بمعاملة وقفل جهاز وإصدار ملكية؛ إلغاء الأوامر وطلبات إشعار الحوادث المعلقة للملكية القديمة، وإقرار الإصدار.

وصول القديم يسقط فوراً؛ الجديد ينتظر تأكيد النسخة؛ أوامر القديم المعلقة تلغى.

BE-04

استقبال رسائل MQTT والتحقق من هوية الجهاز والمخطط والتسلسل

حالة قديمة أو رسالة جهاز آخر لا تحدث الجهاز المستهدف.

BE-05

API حالة الأجهزة: الاتصال المحسوب، الحماية والصفارة والتشخيص، وقت آخر تحديث

لا تختلط المؤشرات الأربعة، وتظهر البيانات القديمة بوضوح.

BE-06

API الأوامر: التحقق من المالك والاتصال والتعارض، حفظ الأمر وOutbox

استجابة الإنشاء PENDING؛ لا نشر إن فشل حفظ الأمر.

BE-07

عامل نشر Outbox عبر MQTT، استقبال ACK، تاريخ انتقال الحالة، المهلة والتأكيد المتأخر ومصالحة TIMED_OUT قبل أمر متعارض

تكرار النشر لا يكرر التنفيذ؛ المهلة لا تتحول إلى نجاح وهمي.

BE-08

استقبال الحوادث والأعطال وعلامة الفقد وإزالة التكرار؛ حفظ wasBuffered وإصدار الملكية؛ إنشاء طلب إشعار الحادثة في معاملة حفظها للملكية الفعالة، ثم إرسال EVENT_PERSISTED بعد الالتزام.

حدث واحد وإشعار واحد رغم إعادة الإرسال.

BE-09

سجلات المالك والأدمن والتنبيهات الإدارية وفصل التاريخ عند نقل الملكية

المالك الجديد لا يرى أحداث المالك السابق.

BE-10

تنفيذ عامل FCM لطلبات الإشعار المحفوظة، وإعادة المحاولة وتسجيل نتيجة التسليم لكل هاتف والتحقق من الملكية قبل الإرسال.

فشل FCM لا يفقد الحادثة؛ لا تدعي الاستجابة أن المالك قرأها.

BE-11

اختبارات وحدة لقواعد العمل، واختبارات تكامل بقاعدة PostgreSQL ووسيط MQTT حقيقيين أو حاويات اختبار

تغطية النقل والتزامن والتكرار والانقطاع، وليس مسارات النجاح فقط.

__الأولوية الأولى للباكند:__ BE-01 ثم BE-02 وBE-04 وBE-05 وBE-06 وBE-07 وBE-08؛ بعدها تكتمل الإدارة والسجلات وFCM. إنشاء سجل حدث وطلب إشعاره في معاملة واحدة؛ نشر MQTT وإرسال FCM يحدثان بعد الالتزام بواسطة عمال مستقلة.

WEB-07

نتائج موثقة وإصلاحات قبل التوسع لأجهزة إضافية.

يصل الجهاز إلى وسيط MQTT عبر TLS. تُقيّد قواعد الوصول لكل جهاز، ويصل Flutter إلى API عبر HTTPS. يمكن استخدام Docker Compose على VPS صغير إذا تلاءم مع سعة الموقع، مع مساحات تخزين دائمة وHealthchecks وأسرار خارج ملفات المشروع؛ لا تجعل الحاويات أو VPS نفسه النسخة الاحتياطية الوحيدة.

## <a id="اختبارات-التكامل-والقبول-بالترتيب"></a>12. اختبارات التكامل والقبول بالترتيب

__رقم__

__سيناريو__

__النتيجة المقبولة__

T-01

الحماية مفعلة؛ افصل الإنترنت ثم أثِر الحساس

تعمل الصفارة محلياً؛ يحفظ الجهاز الحادثة لإرسالها لاحقاً.

T-02

الحماية معطلة؛ أثِر الحساس

لا يطلق الحساس صفارة إنذار، وتبقى النبضات والتشخيص عاملين.

T-03

أرسل ARM من الويب وتأخر ACK

يبقى الأمر PENDING أو TIMED_OUT غير مؤكد؛ تتغير الحماية المعروضة بعد تأكيد الجهاز فقط.

T-04

أعد إرسال الأمر أو الحدث نفسه

ينفذ الأمر مرة واحدة؛ تحفظ حادثة واحدة وينشأ طلب إشعار واحد.

T-05

افتح الحساب على هاتفين وأرسل أمرين متعارضين

يقبل أمر واحد قيد الحسم؛ تتحدث الواجهتان من الحالة المؤكدة.

T-06

إنذار جارٍ ثم MUTE_ALARM

يتوقف الصوت لهذه الحادثة وتبقى الحماية مفعلة؛ حادثة جديدة بعد عودة الحساس تثير الإنذار.

T-07

اختبار صفارة ثم إنذار حقيقي

تنتقل الأولوية للإنذار؛ لا يوقفه مؤقت الاختبار.

T-08

تعطل الخادم أو DB أثناء إرسال الحدث

لا يحذفه ESP32 رغم MQTT PUBACK؛ يعيد إرساله، ويحصل على EVENT_PERSISTED بعد التزام PostgreSQL، مع صف وإشعار واحدين.

T-09

نفاد سعة الأحداث المحلية

يستمر الإنذار المحلي وتظهر علامة بأن السجل غير كامل.

T-10

نقل الجهاز وهو غير متصل

يسقط وصول المالك السابق على الخادم؛ تعاد OWNERSHIP_SYNC عند الاتصال؛ لا يتحكم الجديد قبل إقرار النسخة؛ لا تتسرب سجلات القديم.

T-11

حاول حساب آخر قراءة جهاز أو أمره، وحاول جهاز نشر قناة جهاز ثانٍ

يرفض API وACL كلا الطلبين.

T-12

فشل FCM أو تعطيل إذن الإشعارات

تبقى الحادثة مسجلة وقابلة للعرض؛ تسجل محاولة الإرسال فقط.

T-13

انقطاع المصدر الأساسي ثم إعادة تشغيل الجهاز

يعمل بقدرة البطارية المختبرة؛ يستعيد آخر حماية مؤكدة أو يعلن UNKNOWN إن تلف الإعداد.

T-14

لا توجد وسيلة فحص للحساس أو قياس للبطارية

تظهر UNKNOWN أو غياب القياس؛ لا تعرض «سليم» أو «البطارية فارغة» بلا دليل.

T-15

إعادة تشغيل VPS واستعادة قاعدة بيانات من نسخة

تبدأ الخدمات ويسترد النظام الحالة والسجلات المعتمدة من دون تكرار أو أوامر قديمة.

T-16

ربط أولي لجهاز متصل ثم تأخر إقرار الملكية

يراه المالك PENDING عرضاً محدوداً بلا أوامر أو تاريخ؛ يصبح ACTIVE بعد إقرار الجهاز للإصدار.

T-17

أمر TIMED_OUT ثم أمر متعارض، ووصول تقرير حالة أحدث

يرفض المتعارض قبل المصالحة؛ يقبل وفق الصلاحية بعد تقرير حالة فعلي أحدث أو تأكيد موثوق.

T-18

تغير الحادثة الجارية بين عرضها وإرسال MUTE_ALARM

يرفض الجهاز الكتم إذا لم يطابق target_alarm_event_uid الحادثة الجارية.

T-19

أرشفة جهاز متصل ومحاولة إعادة الاتصال باعتماده السابق

يبطل Broker/ACL الاعتماد وتنتهي جلسة الجهاز؛ لا يستطيع النشر أو الاشتراك ثانية.

T-20

تعطيل حساب مع جلسة ورمز دخول سابقين ثم طلب أمر

يبطل وصوله وتُرفض العملية المحمية فوراً.

T-21

ربط أمر بحادثة أو حادثة بحساس تابع لجهاز آخر

ترفضه قيود FK المركبة على PostgreSQL فعلي.

T-22

كتم إنذار مع بقاء إشارة الحساس قائمة

تصبح الصفارة OFF ويبقى current_alarm_event_uid حتى نهاية الحادثة.

T-23

إعادة حدث من الذاكرة بساعة جهاز غير موثوقة

تظهر wasBuffered ووقت الاستلام وعبارة وقت وقوع غير مؤكد.

T-24

نقل ملكية مع إشعار حادثة معلق وتنبيه إداري مستقل

تلغى الحادثة المعلقة بحالة CANCELLED ويبقى ADMIN_ALERT؛ يرفض فتح تفاصيل إشعار سابق.

T-25

تسجيل جهاز دون device_settings أو دون قيم D-03 معتمدة

تتراجع معاملة التسجيل ولا يظهر جهاز جاهز.

بوابة الإصدار G2: نجاح T-01 إلى T-25 في staging، ثم اختبار ميداني على العتاد الحقيقي. أي فشل في T-01 أو T-02 أو T-10 أو T-11 يمنع إطلاق النظام حتى يعالج، لأنها تمس الإنذار المحلي أو عزل الملكية والأجهزة.

## <a id="تسلسل-المهام-في-لوحة-العمل"></a>13. تسلسل المهام في لوحة العمل

أنشئ هذه المجموعات بهذا الترتيب؛ كل سطر يمكن تحويله إلى Epic، والرموز في الأقسام السابقة إلى مهام:

1. أساس المنتج والعتاد: D-01 إلى D-07 ثم G0؛ يحسم D-08 نطاق التحديث عن بعد مستقلاً عن بوابة الأساس.
2. __العقود والبيئة المحلية:__ MQTT/API وآلات الحالات ثم G1؛ DB-01؛ OPS-01 محلياً؛ HW-01.
3. __الأمان المحلي أولاً:__ ESP-01 إلى ESP-05 واختبارات T-01 وT-02 على جهاز حقيقي.
4. أول شريحة متكاملة: DB-02 إلى DB-04؛ BE-01 وBE-02 (بما في ذلك إقرار الربط الأولي) وBE-04 إلى BE-08؛ ESP-06 إلى ESP-08؛ WEB-01 إلى WEB-04. النتيجة: أمر مؤكد وحادثة محفوظة. DB-02 يتضمن audit_logs، وDB-03 ينشئ alarm_events قبل device_commands، وDB-04 يتضمن admin_alerts وnotifications؛ لا يبدأ BE-08 قبل تطبيقها. تختبر قيود FK المركبة مع الترحيلات التي تقدمها، ولا تؤجل إلى نهاية DB-06.
5. __اكتمال الملكية والعمليات:__ DB-05 إلى DB-07؛ BE-03 وBE-09؛ ESP-09؛ WEB-05 وWEB-06؛ MOB-01 إلى MOB-03.
6. __الإشعارات والهاتف:__ FCM-01 إلى FCM-06؛ BE-10؛ MOB-04 إلى MOB-06.
7. البنية والإطلاق: OPS-02 إلى OPS-08؛ ESP-10؛ BE-11 وWEB-07 وDB-08؛ T-01 إلى T-25 ثم G2.

__الطريق الحرج:__ اختيار العتاد والشرط ← اختبار إنذار محلي ← عقد الرسائل ← تثبيت نموذج الملكية والأمر ← MQTT وOutbox وACK ← تجربة end-to-end ← حالات الانقطاع والنقل ← قبول الإنتاج. يمكن بدء تصميم واجهات Flutter مبكراً، لكنه لا يختصر هذا الطريق.__ تبقى D-01 إلى D-07 بوابة اعتماد قيم حقيقية على العتاد المحدد، ولا تُملأ من التخمين. يضم G1 أمثلة رسائل ورسائل خطأ قابلة للاختبار قبل تثبيت كل طرف.__
