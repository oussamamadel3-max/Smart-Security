# قرار حسم بوابة G1 — نظام الأمان الذكي

**التاريخ:** 2026-11-15  
**المرجع:** خطة تطوير نظام الأمان الذكي v1.0 وSRS v1.0  
**النطاق:** عقد التكامل بين ESP32 وMQTT/Mosquitto وASP.NET Core API وFlutter؛ ليس اعتماد نشر الإنتاج.  
**القرار الحالي:** `G1 = BLOCKED / NOT APPROVED` حتى تقديم أدلة تحقق كاملة. اعتماد تصميم العقد لا يعني اجتياز بوابة الاختبارات.

## 1. القرارات الثابتة في المرجع (لا يعاد فتحها دون طلب تغيير)

1. مصدر الحقيقة في الحماية والصفارة والتشخيص هو آخر حالة فعلية أكدها الجهاز، لا قبول HTTP ولا MQTT PUBACK.
2. حالات الحماية: `ARMED | DISARMED | UNKNOWN`. حالات الصفارة: `OFF | ALARM | TEST | UNKNOWN`. صحة العتاد: `HEALTHY | FAULT | UNKNOWN`. الأوامر: `PENDING | EXECUTED | REJECTED | TIMED_OUT | CANCELLED`. الملكية: `PENDING | ACTIVE | ENDED | CANCELLED`.
3. `COMMAND_ACK` يشمل `commandId` و`ownershipVersion` و`status` ولقطة فعلية كاملة `armState`, `sirenState`, `healthState`, `currentAlarmEventUid`, `confirmedOwnershipVersion` مع `resultStateSequence`. يحدّث الخادم الحالة المؤكدة فقط إن كانت اللقطة أحدث من الحالة المؤكدة المخزنة. `STATE` دورية مستقلة؛ التكرار والأقدم لا يرجعان الحالة للخلف.
4. `stateSequence` تزايدي على مستوى الجهاز ويستمر عبر إعادة التشغيل؛ لا يستخدم `bootId` بديلاً عن هذا الضمان إلا بعقد تسلسل مكافئ معتمد ومختبر. النبضة وحدها لا تعدل حالة الحماية المؤكدة.
5. UTC في الرسائل بصيغة RFC 3339 مع `Z`. يلزم `clockTrusted` حيث يؤثر الوقت على الثقة؛ يرفض ESP32 أي أمر لا يستطيع التحقق من `expiresAt` الخاص به. لا توصف أوقات غير موثوقة بأنها دقيقة.
6. `MUTE_ALARM` يحمل `targetAlarmEventUid` ويستهدف حادثة جارية بعينها؛ كتم الصوت لا ينهي الحادثة ولا يعطل الحماية. يبقى `currentAlarmEventUid` حتى عودة الحساس إلى وضعه الطبيعي.
7. `POST` إنشاء الأمر يتطلب مفتاح idempotency، ويرجع `202 Accepted` و`commandId` و`PENDING`، ولا يُظهر نجاح تنفيذ الجهاز. أخطاء العقد تشمل `401`, `403`, `409`, `503` مع رمز ثابت.
8. الربط الأولي `PENDING` حتى يقر الجهاز نسخة الملكية. نقل الملكية يصبح `ACTIVE` للمالك الجديد داخل معاملة الخادم فوراً، وتسقط صلاحيات القديم في API في اللحظة نفسها، لكن نشر أوامر الجديد ينتظر `OWNERSHIP_SYNC` وإقرار الجهاز. إلغاء الربط يزامن إصدار الملكية أيضاً دون هوية مالك.
9. حفظ الحادثة وطلب إشعارها في معاملة DB واحدة عندما تكون الملكية فعالة؛ `EVENT_PERSISTED` لا يرسل إلا بعد نجاح التزام الحفظ، بما فيه إعادة إرسال حادثة موجودة. لا يعتبر MQTT PUBACK تأكيد حفظ DB.
10. الإنذار المحلي مستقل عن الشبكة/الخادم ما دامت الطاقة والقطع اللازمة تعمل. نطاق v1 هو اهتزاز `SW-420` فقط؛ الحركة/الباب وOTA مؤجلة.

## 2. قنوات MQTT الأساسية

| Topic | الناشر | المشترك | سياسة النقل |
|---|---|---|---|
| `devices/{deviceId}/state` | الجهاز | الخادم | النبضات الدورية QoS 0؛ رسائل الحالة المؤكدة ذات الأثر يجب اختبار موثوقية تسليمها في العقد النهائي |
| `devices/{deviceId}/events` | الجهاز | الخادم | QoS 1، إزالة التكرار بواسطة eventUid/messageId |
| `devices/{deviceId}/acks` | الجهاز | الخادم | QoS 1، إزالة التكرار وتتبع commandId |
| `devices/{deviceId}/commands` | الخادم | الجهاز | QoS 1 للأوامر وOWNERSHIP_SYNC وEVENT_PERSISTED، وعدم استخدام retained للأوامر اللحظية |

الأسماء الواردة من خطة التطوير هي خط أساس مقترح للاعتماد. يلزم تثبيت حقول JSON، حدود الحجم، حدود إعادة المحاولة، وسياسة الرسائل retained في ملف عقد واحد. يكون لكل جهاز هوية اتصال مستقلة؛ ACL يمنع نشر/قراءة قنوات جهاز آخر. اختبار MQTT يجب أن يثبت الرفض فعلياً على broker حقيقي، لا أن يعتمد فقط على فحص داخل الـ API.

## 3. الحقول الأساسية لرسائل العقد

- جميع الرسائل: `schemaVersion=1`, `deviceId`, `messageId`, `messageType`.
- الرسائل الصادرة من الجهاز: `bootId` وعلامة الثقة بالوقت حيث ينطبق، مع `stateSequence` أو `resultStateSequence` للحالة.
- `EXECUTE_COMMAND`: `commandId`, `commandSequence`, `ownershipVersion`, `type`, `expiresAt`، و`targetAlarmEventUid` عند الكتم.
- `COMMAND_ACK`: `commandId`, `ownershipVersion`, `status`, `resultStateSequence`, وحقول لقطة الحالة الكاملة المعتمدة أعلاه، مع رمز سبب عند الرفض.
- `STATE`: `stateSequence`, `confirmedOwnershipVersion`, `armState`, `sirenState`, `healthState`, `currentAlarmEventUid`, `clockTrusted`.
- `ALARM_EVENT`: `eventUid` ثابت، `ownershipVersion`, `sensorKey`, `wasBuffered`, `clockTrusted`, `occurredDeviceAt` (null عند عدم الثقة). توجد مخططات متميزة لإنهاء الحادثة، العطل، وعلامة الفقد.
- `EVENT_PERSISTED`: `eventUid`, `stored=true` بعد commit فقط.
- `OWNERSHIP_SYNC`: `ownershipVersion`, `isLinked` مع إقرار الإصدار عبر `confirmedOwnershipVersion`.

**مطلوب قبل اعتماد G1:** تحويل الأمثلة في الخطة إلى ملفات JSON Schema فعلية بمحددات النوع والإلزام والنسخ، وتغطية رسائل نهاية الحادثة، عطل الجهاز، علامة فقد الأحداث، الربط الأولي، النقل، إلغاء الربط والتكرار. الأمثلة في الخطة توضيحية ولا تُعد Schema ملزماً مكتملًا بذاتها.

## 4. شروط اعتماد G1 (كلها إلزامية)

- [ ] **G1-01** توثيق خط الأساس: نسخة عقود MQTT وOpenAPI وآلات الحالات، تطابق SRS وخطة التطوير، والاتفاق على أسماء القنوات والحقول والأخطاء.
- [ ] **G1-02** ضبط قرار D-03/D-05: TTL موجبة قابلة للتحقق، وسياسة تسلسل آمنة عبر إعادة التشغيل، والتعامل مع الوقت غير الموثوق، وحدود السعة/تخزين الأحداث. أي قيمة غير مختبرة تُعلّم `OPEN`, ولا تصاغ كأنها نهائية.
- [ ] **G1-03** broker Mosquitto محلي أو staging يعمل بهويات مستقلة وTLS/ACL وفق البيئة؛ تجربة مسموح/مرفوض بين جهازين وخادم.
- [ ] **G1-04** اختبارات تطابق مخططات JSON الصادرة والواردة ورفض نسخ/حقول إلزامية/أنواع/هويات غير صالحة، مع تمثيل كل الرسائل المذكورة.
- [ ] **G1-05** أمر ARM/DISARM: API يعيد `202/PENDING`، ثم يسجل ACK التنفيذ أو الرفض دون نجاح وهمي، ويطبق Idempotency/Outbox.
- [ ] **G1-06** اختلاف ترتيب `STATE` و`COMMAND_ACK`، إعادة التسليم، تأخر ACK بعد `TIMED_OUT`، والتعافي/المصالحة: لا تراجع في الحالة المؤكدة؛ تسجل انتقالات الأمر.
- [ ] **G1-07** حدث إنذار مع إعادة الإرسال: صف واحد، إشعار محفوظ مرة واحدة، `EVENT_PERSISTED` بعد Commit، وصمود عند تعطل DB وعدم حذف حدث من جهاز قبل الإقرار.
- [ ] **G1-08** اختبار `MUTE_ALARM` مع نفس معرف الحادثة؛ تغير معرف الحادثة يسبب الرفض، والإنذار الحقيقي يتقدم على اختبار الصفارة.
- [ ] **G1-09** الربط الأولي والنقل والإلغاء: ملكية API صحيحة فوراً، وOWNERSHIP_SYNC بإقرار الإصدار، لا أوامر قديمة، ولا وصول عبر API أو ACL لجهاز أجنبي.
- [ ] **G1-10** تحقق ممثل ESP32 وممثل Backend وممثل Flutter من العقد نفسه باختبارات توافق آلية (أو توثيق ما تعذر على كل طرف مع بقاء البوابة BLOCKED).
- [ ] **G1-11** تقرير دليل فعلي: أوامر التشغيل، بيئة الاختبار، سجل النتائج نجاح/فشل، أسماء ملفات الاختبار، نسخ Schema، وقيود الاختبار وغياب الأسرار في السجلات.

**ملاحظة نطاقية:** التجربة الميدانية الشاملة للإنذار والبطارية واختبارات T-01 إلى T-27 تدخل ضمن مراحل لاحقة وG2؛ لكن أي قرار يتطلب تحقّقاً على العتاد قبل تجميد العقد (مثل التسلسل والوقت الموثوق) يبقى مانعاً لـ G1 إن لم يثبت.

## 5. كيف يتخذ قرار البوابة

- **APPROVED:** كل بنود G1 تحققَت بالأدلة، لا توجد ثغرات تعاقدية حرجة، وتم توثيق موافقة مراجعة العقد من الأطراف المعنية.
- **BLOCKED:** بند واحد إلزامي غير مختبر/فاشل، أو Mosquitto/ESP32 غير متاح لإثبات جزء إلزامي، أو كان مخطط JSON غير مكتمل.
- **CONTRACT DRAFT COMPLETE (NOT G1):** مسموح إذا اكتمل التوثيق واختبارات المحاكاة، لكن تعذر اختبار التسلسل على العتاد أو ACL على broker. لا يعامل كاجتياز G1.

**الحالة المعروفة حتى 2026-11-15:** تقرير `BE-T-10` السابق يصرح أن MQTT الحي غير متاح، وأن بعض المهام منفذة اختبارياً دون إغلاق؛ لا توجد في المواد المتاحة أدلة نجاح كل شروط G1. لذلك **لا يصح إصدار APPROVE TASK CLOSURE أو G1 APPROVED الآن**.

## 6. علاقة G1 بالمهام الحالية

خطة التطوير تستخدم أسماء `BE-04...BE-10`، بينما تقارير تنفيذ Cursor وردت بصيغة `BE-T-05...BE-T-10`. يجب على الوكيل عمل خريطة مطابقات من ملفات المهام الفعلية، لا افتراض تطابق الأرقام. إغلاق المهام المنفردة يحتاج موافقة مستقلة وفق قواعد المشروع، ولا يترتب تلقائياً على مراجعة G1.
