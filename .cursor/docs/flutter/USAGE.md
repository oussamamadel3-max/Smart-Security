# دليل الاستخدام اليومي

استخدم هذا الملف كل يوم أثناء العمل على تطبيق Flutter. لا تحتاج قراءة المهارات أو القواعد قبل كل مهمة — شغّل الأمر، وأعطِ الحد الأدنى من المعلومات، ثم راجع الناتج.

الإطار يعمل فقط إذا فُتح المشروعان معاً: التطبيق + هذا المجلد.

---

## 1. تشغيل الجلسة (مرة في بداية اليوم)

1. افتح مساحة عمل Smart Security (المستودع الجذر) بحيث يظهر `.cursor` مع مشاريع Flutter.
2. تأكد أن الشريط الجانبي يظهر المستودع و`.cursor`، واعمل داخل `security_mobile/` أو `admin_web/`.
3. اعمل داخل ملفات التطبيق (`lib/...`). الإطار يوجّه الوكيل؛ الكود يُكتب في التطبيق.

### إدارة الحالة (مرة لكل مشروع)

المشروع يستخدم **Riverpod أو BLoC — واحد فقط، بلا خلط**.

- تطبيق موجود: الوكيل يكتشف المكدس من `pubspec` والكود (`stack.md` يبقى `auto`). تطبيق GIS الحالي → Riverpod.
- مشروع جديد أو غير محسوم: `/flutter-0-choose_stack` ثم `riverpod` أو `bloc`. يُكتب الاختيار في `stack.md`.
- لا تطلب BLoC على تطبيق Riverpod (أو العكس) إلا كمهمة ترحيل صريحة.

يمكنك أيضاً تمرير المكدس في أول أمر على مشروع فارغ:

```text
/flutter-0-choose_stack
المكدس: bloc
```

مجلد التطبيق على القرص ما زال اسمه `training_indiator_gis_app`. لا تغيّر المسار.

---

## 2. كيف تشغّل أمراً

في الدردشة، اكتب `/` واختر الأمر، أو الصق سطراً مثل:

```text
نفّذ أمر Create Feature.
الفيتشر: courses
الغرض: عرض قائمة الدورات للمستخدم المسجّل
```

القاعدة: **أمر واحد لكل مهمة**. لا تخلط «أنشئ فيتشر + حسّن الأداء + راجع المشروع» في رسالة واحدة.

الوكيل يجب أن:

1. يفحص الكود الموجود أولاً
2. يسألك فقط عما لا يستطيع استنتاجه
3. يولّد أو يعدّل أقل عدد من الملفات
4. يعيد استخدام `lib/core/`
5. لا ينهي العمل قبل `flutter-senior-engineer`

إذا بدأ يخترع معمارية جديدة أو `Dio()` محلي أو `HttpFailure` — أوقفه وقل: التزم بالقواعد والمهارة.

---

## 3. ماذا تختار اليوم؟

ابدأ من السؤال الأول. لا تقفز إلى المراجعة قبل أن يستقر السلوك.

| إذا كنت تريد... | الأمر | لا تستخدمه لـ |
|---|---|---|
| تثبيت Riverpod أو BLoC للمشروع | `/flutter-0-choose_stack` | ترحيل تطبيق يستخدم المكدس الآخر أصلاً |
| شاشة / موديول جديد | `/flutter-1-create-feature` | تعديل فيتشر موجود |
| ربط endpoint بفيتشر موجود | `/flutter-2-integrate-api` | إنشاء فيتشر من صفر |
| مراجعة فيتشر واحد (بدون تعديل) | `/flutter-3-review-feature` | إعادة كتابة الكود |
| إكمال Create/Read/Update/Delete | `/flutter-4-create-crud` | فيتشر غير موجود بعد |
| Login / refresh / حماية المسارات | `/flutter-5-implement-auth` | شاشة عادية تحتاج توكن فقط |
| قوائم طويلة / infinite scroll | `/flutter-6-implement-pagination` | تحميل كل البيانات دفعة واحدة «مؤقتاً» |
| عمل بدون نت / كاش | `/flutter-7-add-offline-cache` | تخزين توكن (هذا Auth) |
| تنظيف كود بدون تغيير سلوك | `/flutter-8-refactor-feature` | إضافة وظيفة جديدة |
| شاشة بطيئة / جank | `/flutter-9-optimize-performance` | تخمين التحسين بدون قياس |
| مراجعة Senior لفيتشر أو PR | `/flutter-10-senior-review` | توليد كود |
| تقييم المشروع كله | `/flutter-11-review-project` | مهمة فيتشر واحد |

مهارات بلا أمر، تُذكر بالاسم عند الحاجة:

- `flutter-senior-engineer` — قائمة «هل انتهى العمل؟»
- `flutter-write-adr` — قرار غيّر طريقة تواصل الطبقات (بعد Refactor عادة)

## 4. نصوص جاهزة (انسخ واملأ)

### تثبيت المكدس (مشروع جديد فقط)

```text
/flutter-0-choose_stack
المكدس: <riverpod / bloc>
```

لا تستخدمه لترحيل تطبيق يعمل مسبقاً على المكدس الآخر.

### فيتشر جديد

```text
/flutter-1-create-feature
الاسم: <courses>
الغرض: <عرض دورات المستخدم>
النوع: <قراءة فقط / CRUD>
المكدس إن كان المشروع جديداً: <riverpod / bloc>
فيه فورم؟ <نعم/لا>
أوفلاين؟ <لا / كاش قراءة / كتابة أوفلاين>
مسار API إن وُجد: <GET /api/...>
بيانات حساسة أو جهة حكومية؟ <نعم/لا>
```

الحد الأدنى: الاسم + الغرض. الباقي اختياري إذا كان واضحاً من المشروع.

### ربط API

```text
/flutter-2-integrate-api
الفيتشر: <courses>
المنهج: <GET>
المسار: </api/courses>
يحتاج توكن؟ <نعم>
الرد: <الحقول الأساسية أو مثال JSON>
```

لا تخترع عقد API. إذا كان العقد ناقصاً يجب أن يسألك الوكيل لا أن يخمّن.

### CRUD على فيتشر موجود

```text
/flutter-4-create-crud
الفيتشر: <courses>
العمليات الناقصة: <Create, Update, Delete>
الحذف يحتاج تأكيد. التحديث التفاؤلي يتراجع لنفس الحالة السابقة عند الفشل.
```

### توثيق

```text
/flutter-5-implement-auth
المطلوب: <إكمال refresh / حماية مسار جديد / logout>
لا مسار تنقّل ثانٍ إلى login. استخدم مالك الجلسة (Riverpod: authSessionProvider / BLoC: AuthCubit) وauthGuardRedirect فقط.
```

### ترقيم صفحات

```text
/flutter-6-implement-pagination
الفيتشر: <courses>
النوع: <page / offset / cursor>
حجم الصفحة: <20>
الفلاتر الحالية تبقى. تغيير الفلتر يلغي الطلب القديم.
```

### أوفلاين

```text
/flutter-7-add-offline-cache
الفيتشر: <courses>
النطاق: <كاش قراءة فقط / كتابة أوفلاين كاملة>
```

اسأل نفسك قبل الكتابة أوفلاين: هل المستخدم يعدّل بدون نت؟ إن لا، اختر كاش قراءة فقط.

### إعادة هيكلة

```text
/flutter-8-refactor-feature
الفيتشر: <auth>
المشكلة: <God Object / تكرار / ميثود أطول من ~25 سطراً>
لا تغيّر السلوك. تغيير هيكلي واحد في هذه الجولة.
```

إذا تغيّرت طريقة تواصل الطبقات، اطلب بعدها: `اكتب ADR باستخدام flutter-write-adr`.

### أداء

```text
/flutter-9-optimize-performance
الشاشة: <home>
العَرَض: <تمرير متقطع / إقلاع بطيء / الذاكرة تكبر>
لا تعدّل كوداً قبل قياس DevTools. أعطني الرقم قبل وبعد.
```

أنت تشغّل DevTools؛ الوكيل يقترح القياس ولا يستبدله.

### مراجعة

```text
/flutter-3-review-feature
الفيتشر: <auth>
لا تعدّل الكود. تقرير مع أولويات فقط.
```

```text
/flutter-10-senior-review
النطاق: <الفيتشر أو الـ PR>
الغرض: <مراجعة عادية / تجهيز إصدار>
```

```text
/flutter-11-review-project
راجع lib/features وlib/core.
أخرج جرداً + مشاكل عابرة للفيتشرز + backlog مرتب.
```

## 5. ترتيب يوم عمل نموذجي

**بناء شيء جديد**

1. `/flutter-1-create-feature`
2. إن وُجد API بعد ذلك: `/flutter-2-integrate-api`
3. إن نقصت عمليات: `/flutter-4-create-crud`
4. قائمة طويلة: `/flutter-6-implement-pagination`
5. إن لزم: `/flutter-7-add-offline-cache`
6. `/flutter-3-review-feature` قبل الدمج

**صيانة**

1. تحديد: إصلاح سلوك أم تنظيف أم بطء؟
2. سلوك جديد → الأمر المناسب من الجدول (ليس Refactor)
3. تنظيف → `/flutter-8-refactor-feature`
4. بطء → `/flutter-9-optimize-performance` بعد قياس
5. قبل الدمج → `/flutter-3-review-feature` أو `/flutter-10-senior-review`

**لا تبدأ بـ** `/flutter-11-review-project` كل يوم. هذا للأسبوع أو قبل إصدار.

## 6. متى تعتبر المهمة منتهية؟

ارفض الناتج إذا اختل بند واحد:

- الطبقات محترمة: الواجهة لا تستدعي Api/DTO، والـ Domain بلا Flutter
- الحالة عبر متحكّم واحد: ViewModel=Notifier (Riverpod) أو Cubit/Bloc (BLoC) — ليس الاثنين
- الأخطاء: `Result` → `ErrorMapper` → `FailureHandler` → ويدجت `My*`
- النصوص في `app_en.arb` و`app_ar.arb` معاً، والقراءة بـ `context.tr`
- التوكن في `SessionStorage` فقط
- GET يُعاد عبر `executeWithRetry()` — POST/DELETE لا يُعادان تلقائياً
- رفع / تحميل / ترقيم / بحث: `CancelToken` + dispose (`ref.onDispose` أو `close()`)
- اختبارات UseCase وRepository على الأقل
- لا `HttpFailure` ولا `Dio()` داخل الفيتشر ولا `context.go(login)` من ViewModel عند فشل التوثيق

## 7. أخطاء شائعة

| لا تفعل | افعل |
|---|---|
| «اكتب فيتشر الدورات بالكامل مع كاش وأداء ومراجعة» | أمر واحد ثم التالي |
| إنشاء فيتشر موجود مسبقاً بـ Create Feature | Integrate API / CRUD / Refactor |
| مراجعة تطلب إعادة كتابة من تلقاء نفسها | «لا تعدّل إلا إذا طلبت» |
| كاش كتابة أوفلاين لشاشة عرض فقط | كاش قراءة |
| تحسين بلا رقم DevTools | قياس ثم أمر الأداء |
| ابتكار `authStateProvider` أو `HttpFailure` | الأسماء الموجودة في القواعد |
| وضع توكن في SharedPreferences | `SessionStorage` |

## 8. ماذا تراجع أنت يدوياً؟ (دقيقتان)

بعد أن يسلّم الوكيل:

1. هل الملفات تحت `lib/features/<name>/` بالطبقات الصحيحة؟
2. هل أضيف مسار في `AppRouter` / `AppRoutes` إن كانت شاشة جديدة؟
3. هل المفاتيح الجديدة في ملفات الترجمة كلها؟
4. هل توجد اختبارات وليس فقط UI؟
5. هل لم يُمس `lib/core/` إلا عند الحاجة الحقيقية (شبكة، خطأ، راوتر)؟

إذا فشل بند: أعد نفس الأمر مع التحديد («أصلح الترجمة الناقصة فقط») بدل بدء مهمة جديدة واسعة.
