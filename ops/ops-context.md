# سياق المشروع — التشغيل والبيئات (`ops`)

السياق العام: [`../system-context.md`](../system-context.md) · التقدّم: [`ops-progress.md`](./ops-progress.md) · قرارات مالك: [`../docs/reports/integration/G0-G1-OWNER-DECISIONS-REPORT.md`](../docs/reports/integration/G0-G1-OWNER-DECISIONS-REPORT.md)

## الهوية

| الحقل | القيمة |
|--------|--------|
| المسؤولية | Compose محلي، عزل بيئات، نشر، صحة خدمات، نسخ/استعادة، مراقبة، تجربة ميدانية |
| التقنية | Docker Compose · PostgreSQL · Mosquitto (أو مكافئ) · TLS/ACL |
| مسار العمل | `ops/` — حالياً تخطيط فقط |
| لا يملك | منطق أعمال API · firmware · شاشات Flutter · نص عقود G1 |

## مبادئ ملزمة

- لا أسرار إنتاج في Git أو صور عامة.
- عزل كامل بين dev / staging / production (قواعد، وسيط، Firebase، اعتمادات أجهزة).
- النسخ لا يُقبل بوجود ملف فقط — يلزم إثبات استعادة موثّق.
- يسرّع عمل الباك إند والـESP محلياً قبل VPS كامل.
- اعتماد Backend `T-02` يضيف متطلبات تشغيل JWT وRefresh/جلسات وCookies/CSRF؛ يظل تشغيل الخدمات ونشرها مسؤولية `ops`.
- `User Secrets` للتطوير المحلي فقط؛ الإنتاج وstaging يحتاجان مصدراً آمناً للأسرار ومفاتيح توقيع JWT منفصلة لكل بيئة، وآلية تدوير واسترجاع موثّقة.
- فصل فحص حياة العملية (`liveness`) عن جاهزية الخدمة (`readiness`)؛ نجاح `/health` لا يثبت سلامة MQTT/Outbox/FCM.
- `G1` و`G2` لم يُعتمدا؛ لا يُستدل بنجاح اختبارات Backend على نجاح broker أو النشر أو العتاد.

## قرارات وموانع

- اسم/إصدار صورة الوسيط يجب توثيقهما عند أول Compose.
- مسودة ACL من `integration` مفيدة قبل تثبيت قنوات الإنتاج؛ يجب اختبار المنع والسماح للنشر والاشتراك لكل جهاز، وعدم الخلط بين نجاح بيئة محلية واعتماد `G1`.
- وفق تقرير تنفيذ Backend `T-02`: API المصادقة والجلسات وإدارة المالك موجودة ومختبرة محلياً؛ عمال MQTT/Outbox/FCM غير منفذين بعد، فلا تُدرج في خدمة منشورة حالياً.
- HTTPS فعلي، وتكوين `Secure` Cookie و`SameSite` و`Path` و`CORS` وCSRF/Origin في staging لم يُتحقق منها بعد؛ تُغطى ضمن `OPS-T-02` و`OPS-T-03`.

## ما أُنجز فعلياً (حتى الآن)

- ملفات التخطيط فقط؛ لا `docker-compose` في المجلد بعد.
