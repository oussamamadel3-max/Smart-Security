- [ ] الحالة: لم تبدأ
- SRS/خطة: **P2** — قاعدة ووسيط تجريبي

- اختبار ACL يجب أن يثبت السماح بنشر/اشتراك الجهاز في قنواته المصرح بها، ورفض publish وsubscribe إلى قنوات الجهاز الآخر، ورفض مجهول الهوية؛ ولا يُعد ACL محلياً موافقة على عقد `G1`.

- البطاقات:

## T-03 نشر الخدمات والصحة

- [ ] الحالة: لم تبدأ
- خطة: `OPS-02` `OPS-04` `OPS-05`
- تعتمد على: `T-02`؛ بناء قابل للنشر من `security_backEnd` (وواجهات عند الحاجة)
- المطلوب: نشر API الحالي من `security_backEnd` (JWT/الجلسات وإدارة المالك) وPostgreSQL ووسيط MQTT عند الحاجة بحدود شبكة مضبوطة؛ **لا تُنشر عمال MQTT/Outbox/FCM إلا بعد تنفيذ مهامها والتحقق من صورها**. HTTPS للواجهات؛ ضبط Reverse Proxy وForwarded Headers الموثوقة، وشهادات TLS.
- اختبارات staging على HTTPS حقيقي: `Secure`/`HttpOnly`/`SameSite`/`Path` للـCookie، Origin/CSRF المقبول والمرفوض، CORS مع credentials وOrigin مسموح/مرفوض، عدم تسريب الرموز في HTTP أو سجلات الحاويات.
- فصل `/health` أو probes إلى `liveness` (العملية حية) و`readiness` (DB/الخدمات المطلوبة جاهزة)؛ أعطال التبعيات لا تخلق حلقة إعادة تشغيل غير مبررة؛ إعادة تشغيل تلقائي؛ نسخة نشر محددة؛ تطبيق الترحيلات بمراجعة ونسخة قبل التغيير وخطة رجوع.
- القبول: PostgreSQL غير عام؛ الوسيط يرفض المجهول والقناة الأجنبية في النشر والاشتراك؛ تعود الخدمات **المنفذة فقط** بعد restart؛ نتائج HTTPS وCookie/CSRF/CORS موثقة؛ liveness/readiness قابلة للتمييز، دون اعتبار نجاح healthcheck دليلاً على اكتمال السلسلة التشغيلية.
- البطاقات:
  - [ ] OPS-02 نشر معزول + MQTT/TLS
  - [ ] OPS-04 بدء/إيقاف وصحة ومساحات دائمة
  - [ ] OPS-05 نشر آلي/إصدار محدد + خطة رجوع
  - [ ] اختبار HTTPS حقيقي لـJWT Refresh Cookie وCSRF/Origin/CORS
  - [ ] probes منفصلة لسلامة العملية وجاهزية التبعيات؛ اختبار فشل قاعدة البيانات
  - [ ] قائمة الخدمات المنشورة مقيّدة بما نُفذ فعلياً في Backend

## T-04 النسخ الاحتياطي واختبار الاستعادة

- [ ] الحالة: لم تبدأ
- SRS: `NFR-007`؛ `DB-08` / `OPS-06`
- تعتمد على: `T-03` staging على الأقل
- المطلوب: نسخ PostgreSQL مشفّر يومي خارج الخادم، مع تحقق سلامة النسخة وقابلية قراءتها؛ اختبار استعادة DB كاملة على بيئة منفصلة وتوثيق المدة الفعلية مقابل **هدف RTO ≤ 4 ساعات وRPO ≤ 24 ساعة** (القيم أهداف لا نتائج محققة مسبقاً).
- خطة **استعادة الخدمة** تشمل كذلك ملفات إعدادات broker وACL وشهادات TLS والتكوين التشغيلي مع استرجاع الاعتمادات من مدير الأسرار الآمن، وفحص إعادة تشغيل API/الوسيط ومواءمة مفاتيح JWT بحيث لا تُفقد صلاحية الجلسات خطأً؛ لا توضع الأسرار في مستودع الكود أو نسخة DB.
- تنبيه عند فشل النسخ أو الاختبار، وجدولة مراجعة دورية لعملية الاستعادة.
- القبول: إثبات استعادة قاعدة البيانات وإعادة تشغيل خدمة مع إعدادات broker وACL والشهادات/مصدر الأسرار موثّق، مع قياس RTO/RPO ومقارنته بالأهداف؛ لا الاكتفاء بوجود ملف النسخة أو مجرد اتصال PostgreSQL.
- البطاقات:
  - [ ] جدولة النسخ خارج المضيف
